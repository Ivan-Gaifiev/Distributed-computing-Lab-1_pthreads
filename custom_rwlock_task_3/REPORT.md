# Лабораторная работа 1, часть 3: блокировка чтения-записи

## Алгоритм

Реализована собственная `my_rwlock_t`: мьютекс, две условные переменные, счётчики активных и ожидающих читателей, ожидающих писателей и флаг активного писателя.

Все изменения состояния происходят под внутренним мьютексом. Читатель ждёт, пока активен писатель или есть ожидающий писатель. Писатель ждёт отсутствия активных владельцев. Ожидания находятся в циклах `while`: сигнал означает не передачу владения, а необходимость повторно проверить условие допуска. После допуска внутренний мьютекс освобождается, поэтому читатели работают параллельно.

При освобождении последним владельцем сначала пробуждается один ожидающий писатель. Если писателей нет, пробуждаются все ожидающие читатели. Если читатели ещё активны, писатель остаётся ждать последнего. Инварианты: не более одного активного писателя; при активном писателе активных читателей нет.

Политика даёт приоритет писателям, но не FIFO и не строгую справедливость: непрерывная очередь писателей может задерживать читателей, порядок писателей не гарантирован. Рекурсивный захват, upgrade, timed/try-вызовы, отмена ожидающих потоков и отслеживание владельцев не реализованы. Вызовы возвращают коды ошибок в стиле pthreads. Уничтожение разрешено после завершения всех пользователей; при наличии владельцев или ожидающих возвращается `EBUSY`.

## Односвязный список и интерфейс

Упорядоченный список без повторов взят из `pth_ll_rwl.c`. `Member` защищён чтением; `Insert` и `Delete` — записью на всё время операции. В обоих режимах исполняется один код списка, выбор блокировки использует одинаковые указатели на функции. Аргументы потоков передаются структурами. Остаток операций распределяется между первыми потоками; счётчики локальны и объединяются после завершения измерений. При частичном отказе создания потоков старт отменяется, созданные потоки пробуждаются и присоединяются.

Команды сборки, запуска и описание CSV приведены в [README.md](README.md). Из Python запускаются только проверки и процессы программы; параллельные операции со списком реализованы на C с pthreads.

## Методика измерений

Начальные размеры: 100 и 1000; операций: 100,000; смеси поиска/вставки/удаления: 100/0/0, 90/5/5 и 50/25/25 процентов. Число потоков: 1, 2, 4, 8. Для каждой конфигурации и режима сделан один прогрев и 10 измерений. Прогревочные результаты сохранены отдельно и в статистику не включаются.

Перед каждым запуском создаётся новый список с равномерно расположенными уникальными ключами `floor(i*key_range/initial)`. Диапазон `[0,key_range)` равен удвоенной начальной длине, вместо 100000000 в исходном примере. Это повышает вероятность успешного поиска и удаления. Нагрузка содержит заданные количества операций каждого типа (для произвольных долей используются целые части произведений, остаток — удаления), затем перемешивается. Ключи и порядок генерируются SplitMix64 с seed=1 заранее. Контрольная сумма `workload_id` проверяет совпадение нагрузки между режимами и числами потоков. Планировщик может менять взаимный порядок операций, число успешных операций и итоговый список.

Таймер `clock_gettime(CLOCK_MONOTONIC)` запускается главным потоком после готовности всех рабочих потоков, непосредственно перед открытием стартового шлюза. Конец — максимальная отметка рабочего потока после его последней операции. В интервал входят пробуждение из шлюза, блокировки, обход списка, выделение и освобождение узлов и локальные счётчики; создание потоков, подготовка, join, объединение результатов, проверка списка и CSV исключены. Для потоков без операций учитывается время выхода из шлюза.

Все процессы запускаются последовательно; порядок режимов чередуется между повторами. Привязка к ядрам не используется. Медиана — среднее двух центральных значений из 10; минимум сохранён отдельно. Пропускная способность = 100000 / медиана времени; ускорение = медиана одного потока / медиана данного числа потоков для той же смеси, длины и блокировки.

Эффективность рассчитывается по формуле `E = S/p = T1/(p*Tp)`, где `S` — ускорение, `p` — число рабочих потоков, `T1` и `Tp` — медианы времени с одним и с `p` потоками. В качестве последовательного базового времени используется однопоточный запуск того же режима. В `summary.csv` поле `efficiency` хранит долю, а в таблицах отчёта эффективность указана в процентах (`100*E`). 

## Среда

Измерения выполнены в Windows с GCC и winpthreads. Команды сборки приведены в README, флаги — в Makefile. Результаты зависят от среды; для другой системы нужны отдельные измерения.

Подробные сведения о компьютере и локальные пути сохраняются только в `metadata.json`, исключённом из Git.

## Проверка корректности

Пройдены проверки одновременных читателей, ожидания последнего читателя, приоритета ожидающего писателя, пробуждения после писателя, исключительности записи и устойчивости к пробуждению без изменения условия. Сценарии используют условные переменные; регистрация ожидающих наблюдается под внутренним мьютексом с `sched_yield`, без `sleep`. Тайм-ауты служат только для обнаружения зависания.

Для обоих режимов пройдена смешанная нагрузка из 8 потоков по 2000 захватов с проверкой исключительности и вставками/поиском/удалением. Проверены операции с пустым списком, началом, серединой, концом и повторным ключом; проверяющий код обнаруживает нарушенный порядок и циклы. CLI-проверки охватывают остаток деления, число потоков больше числа операций, пустой начальный список, чистые смеси, одинаковый seed, 19 некорректных вводов и искусственный отказ третьего `pthread_create` после двух успешных созданий. Каждый измеряемый запуск также проверяет порядок, отсутствие повторов/циклов, точное количество операций и баланс длины списка.

Сводный журнал: [tests.txt](results/tests.txt). Проверки подтверждают пройденные сценарии, но не являются формальным доказательством отсутствия всех гонок.

## Выводы

По медиане собственная блокировка быстрее библиотечной в 15 из 24 сопоставленных конфигураций. Отношение времени pthread/custom больше 1 означает преимущество custom.

Наибольшее отношение pthread/custom: 2.200, длина 100, смесь 100/0/0, потоков 4.

Наименьшее отношение pthread/custom: 0.157, длина 100, смесь 50/25/25, потоков 8.

Наибольшее ускорение относительно одного потока своей блокировки: 1.610 (pthread, длина 1000, смесь 100/0/0, потоков 2).

Разница отражает не только стоимость блокировок, но и их политику допуска, планирование потоков и накладные расходы. Вставки и удаления сериализуют весь список; каждый вход и выход собственной блокировки также использует общий внутренний мьютекс. Увеличение числа потоков поэтому не обязано ускорять программу. Политика библиотечной блокировки используется по умолчанию и не приравнивается к политике собственной.

Без закрепления потоков, контроля частоты CPU и изоляции фоновой нагрузки результаты имеют шум. Небольшие различия медиан не следует считать доказанным преимуществом.
